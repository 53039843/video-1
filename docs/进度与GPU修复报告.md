# 视频本地化程序进度与 GPU 修复报告

## 结论

本轮已完成三项关联问题的修复，并已重启本地服务加载新代码。页面中同一条“媒体探测 5%”重复出现，并不是同一任务被启动十次，而是前端每两秒恢复任务状态时，把后端持久化的同一条历史日志反复追加。任务实际停在 5% 的位置是 **FFmpeg 音频提取子进程**；原视频本身、音轨和中文路径均无损坏。GPU 未参与语音识别则是因为项目环境缺少 CTranslate2 所需的 CUDA 12 cuBLAS 与 cuDNN 动态库。

| 问题 | 已验证根因 | 修复状态 |
|---|---|---|
| 同一秒、同一内容的 5% 日志重复十次 | 前端轮询与实时日志流共同调用 `addLog`，但没有稳定事件键去重 | 已修复 |
| 进度长期停在“媒体探测 5%” | 音频提取采用无进度的阻塞调用，且未显式禁止 FFmpeg 读取标准输入 | 已修复 |
| GPU 没有参与 faster-whisper | 缺少 `cublas64_12.dll` 及相应 cuDNN 运行库 | 已修复 |
| GPU 环境异常时任务直接失败 | 原流程固定使用 CPU，亦没有显式设备状态和回退信息 | 已加入 GPU 优先、CPU 自动回退 |

## 实施改动

正式流水线的音频提取现已使用 FFmpeg 的机器可读进度输出，并加入 `-nostdin`，防止后台服务中的 FFmpeg 意外等待标准输入。界面进度会从 **6% 持续推进到 15%**，日志同时显示“已提取 X/Y 秒音频”，随后进入 18% 的本地语音识别阶段。因此，即使未来遇到异常媒体，也能直接判断停滞发生在哪个媒体时间点，而不再只有一个静态的 5%。

| 文件 | 关键改动 |
|---|---|
| `real_media_pipeline.py` | 音频提取改用真实媒体时间驱动的进度封装；加入 `-nostdin`；ASR 优先使用 CUDA FP16；CUDA 异常时记录原因并回退 CPU INT8 |
| `control_panel_v3.html` | 以任务编号、时间、进度、阶段和消息组成稳定事件键，历史轮询与实时流统一去重；新任务开始时清空去重集合 |
| `.venv311` 项目环境 | 安装项目隔离的 CUDA 12 cuBLAS、cuDNN 与 NVRTC 运行库，不修改系统级环境变量 |

项目运行时只将 `.venv311\Lib\site-packages\nvidia\...\bin` 加入**当前服务进程**的 DLL 搜索路径，不写入 Windows 系统 PATH。这样既满足本地 GPU 推理，又避免污染全局环境。GPU 初始化或推理阶段若出现兼容性错误，任务会将具体异常写入进度日志，并自动切换到 CPU，而不是无提示卡住。

回归使用此前发生问题的同一视频，媒体时长为 **2785.044 秒**。完整音频提取生成 89,123,928 字节的 16 kHz 单声道 WAV，仅耗时 **2.728 秒**，证明源媒体、音轨、中文文件名与长输出路径均可正常处理。正式进度封装记录到 7%、13%、15% 三个单调递增事件，重复事件数为零。

| 验证指标 | 实测值 | 判定 |
|---|---:|---|
| 原视频时长 | 2785.044 秒 | 有效长视频样本 |
| 完整音频提取耗时 | 2.728 秒 | 正常 |
| 音频输出大小 | 89,123,928 字节 | 正常 |
| 音频阶段进度 | 7% → 13% → 15% | 单调递增 |
| 重复进度事件 | 0 | 通过 |
| 60 秒音频 GPU ASR 耗时 | 1.912 秒 | 正常 |
| ASR 识别片段数 | 38 | 有真实输出 |
| GPU 峰值利用率 | 37% | GPU 确实参与计算 |
| GPU 显存峰值 | 5642 MiB | CUDA 模型已加载 |
| 综合回归 | `validation_passed = true` | 通过 |

> GPU 利用率是瞬时采样值；tiny 模型处理 60 秒音频只需约 1.9 秒，因此并不会长时间保持高负载。判断 GPU 是否工作应结合 CUDA 推理成功、显存变化和峰值利用率，而不是只观察任务全程的平均占用。
