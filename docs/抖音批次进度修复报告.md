# 抖音批次进度修复报告

## 诊断结论

“已解析 1 条抖音链接，按顺序处理”后长期显示 `0% 队列`，由三个后端缺陷共同造成。首先，抖音批次线程在写入“下载完成”日志时把 `message` 与 `progress` 参数顺序传反，字符串被当成数值转换。其次，日志函数在进度值为整数 `0` 时仍调用 `.is_integer()`，导致线程在首条 0% 日志处直接抛出异常。最后，子任务原先要等下载完成后才加入父批次的 `items`，因此下载期间页面看不到子任务，父任务也没有镜像子任务阶段。

只读诊断显示，问题批次父任务保持 `queued / 0%`，子任务已经进入 `failed` 或没有正常写入状态；下载目录中没有对应的处理中临时文件。该现象与页面只显示一条 0% 日志完全一致，并非 ASR 或 GPU 阶段停滞。

| 现象 | 直接原因 | 结果 |
|---|---|---|
| 0% 队列不动 | 批次线程在首条日志附近异常退出 | 父任务不进入下载或媒体探测 |
| 日志不再增加 | `log()` 收到错误类型或参数错位 | 后台线程提前结束 |
| 页面看不到子任务 | 子任务在下载完成后才加入 `items` | 刷新期间无法显示下载状态 |
| 父任务不显示ASR/烧录进度 | 没有把子任务阶段映射到父任务 | 用户只能看到静态0% |

## 修复内容

现在批次线程启动后立即将父任务状态写为 `processing`，并在下载前创建 `downloading / 0%` 的子任务，随后持久化到本地任务数据库。下载完成后只更新该子任务的路径与状态，不再延迟创建记录。日志进度统一先转为浮点数再规范化，因此 `0`、`100` 和小数进度都能安全写入。

父任务现在会镜像当前子任务的阶段和进度。对于单条视频，媒体探测、语音识别和字幕烧录会直接显示对应阶段；多条视频则按批次序号折算为整体进度。例如第 2 条视频的 35% 会映射到整体进度区间，避免父任务在子任务处理期间停留在0%。

| 代码位置 | 改动 |
|---|---|
| `local_app_v2.py:94-98` | 修复整数进度 `.is_integer()` 异常 |
| `local_app_v2.py:165-184` | 增加父批次进度镜像与子任务阶段传播 |
| `local_app_v2.py:226-267` | 下载前创建并持久化子任务；修复日志参数顺序；补充批次失败收尾 |
| `control_panel_v3.html` | 保留此前的日志事件键去重，避免刷新后同一日志重复显示 |
